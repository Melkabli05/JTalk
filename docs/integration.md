# JTalk integration and release evidence

The Angular Material 21 application in this repository is the implementation target. The local JTalk checkout supplies the legacy Optimus/PrimeNG flows. The two Java 25 Micronaut 5 services own the HTTP contracts. The endpoint inventory covers 22 user operations and 32 voice-service operations, including the signed webhook. Each table identifies its source revision. [API fields, operations and validation](api.md)

## System and trust boundaries

| Component | State and responsibilities |
| --- | --- |
| Auth0 | Universal Login handles registration, login and logout. The browser requests the shared JTalk API audience. Both services verify JWT signature against tenant JWKS, issuer, audience, expiry and a UUID user claim (default `https://jtalk.app/user_id`). Profile creation after a missing `GET /me` is separate from registering the Auth0 identity. Deleting the JTalk profile leaves Auth0 identity management with Auth0. |
| User service | JDBC repositories and Flyway own profiles, uploaded pictures, languages, follows and blocks in PostgreSQL. Redis caches summaries and social sets. Committed profile changes publish on `user-events`. Batch summaries omit language matrices. Individual profiles carry them. Blocking severs follows both ways and affects directory results. |
| Voice service | PostgreSQL owns room definitions. Redis holds the live roster, stage, hand queue, leases, chat and reaction state. Lua performs atomic stage changes. Redis pub/sub distributes the hallway feed. LiveKit server SDK calls issue room-scoped grants and change participant permissions. The signed webhook updates media presence. |
| Browser | Auth0 access tokens authenticate same-origin HTTP and SSE. The current SDK settings persist refresh tokens in browser storage. The ephemeral LiveKit join token stays in memory. Room audio and server data travel directly to the returned LiveKit URL. The only stored room reference is an ID in session storage. |

One host can have one open room. Creating another returns the existing session. Room size is 2–12 stage seats including the host. Joining is as a listener unless a seat already belongs to the caller. A participant may claim an open seat or raise a hand. Vacating a seat can promote the next queued participant. Host departure and closing the room are distinct actions. Media disconnect gives seated non-host speakers a grace lease (30 seconds by default). Redis expiry notifications and delivery of the LiveKit webhooks matter for recovery.

Both services use RFC 9457 problem documents. A client should preserve the original status and detail, including a conflict on profile creation or a throttled comment. The username can change under the configured interval despite the older README saying it is fixed. Updates that include learning languages replace the entire list. The backend validates both membership and host-only actions. Comment deletion, chat mute, pinning, stage moderation, kicking, editing and closing are host operations. A kick records the backend's room ban. There is no separate invitation acceptance, moderator role, configurable timeout or transfer-host API.

## Transport contracts

| Channel | Messages and recovery |
| --- | --- |
| Authenticated HTTP SSE, `GET /api/v1/voice-rooms/feed` | `SNAPSHOT` carries `rooms`. `ROOM_OPENED` and `ROOM_UPDATED` carry `room`. `ROOM_CLOSED` carries `roomId`. `ROOM_STATS` carries `roomId` and `live` with speakers, participantCount and handRaiseCount. Empty named pings occur every 20 seconds. Reconnecting starts a new snapshot. The Material hallway also has a REST polling fallback. |
| LiveKit `room-events` | JSON with type, roomId and timestamp. Stage and hand events carry a stage snapshot, speaker reconnect events identify targetUserId, presence carries joined/left IDs and count, room edits carry settings, reaction bursts carry user/reaction pairs and profile updates carry profileUpdate. The Java envelope and enum also define comment pin events. |
| LiveKit `room-chat` | Posts carry the comment, deletes and pins identify commentId. Reaction events carry commentId, targetUserId, reaction and previous. Null reactions remove the previous selection. Chat mute events identify targetUserId. Topic changes carry the replacement topic or clear it. Snapshot pin state lives on each comment as pinnedAt. Muted-user lists are viewer-dependent. |
| LiveKit media and webhook | Create/join/stage-join returns room, role, canPublishAudio, liveKitUrl and liveKitToken. The join token defaults to two minutes. Listeners subscribe, publishers can send microphone audio only, clients cannot publish data. The client accepts server-originated packets. LiveKit sends signed participant join/leave notifications directly to the voice service at `POST /webhooks/livekit`. There is no JTalk application WebSocket endpoint or client heartbeat. |

## Legacy flows and Material coverage

| Flow | Material entry point and integration |
| --- | --- |
| Sign in, return to a room, onboard, profile and appearance | Auth0 redirect, guarded shell, profile read/create/patch, native and learned languages, versioned avatar upload and account deletion. Appearance is a browser preference. The session and profile services remain shared. |
| Directory and relationships | People uses backend matchmaking and prefix search, follow/unfollow and block. Profile Overview loads followers, following and blocked accounts, supports pagination and unblocking. Room participant profiles resolve by UUID. |
| Hallway and host tools | Room cards consume authenticated feed/list calls and batched identities. Creation consumes the session returned by the service. Hosts edit title, topic and seats, moderate participants and close rooms. |
| Stage and presence | LiveKit drives remote audio, mute, active speakers and connection status. REST supplies authoritative roster and hand queue. The stage supports direct seat claims, hand raise/lower, host promotion/demotion/mute and removal. Reconnection refreshes room, roster, stage and chat. |
| Chat and reactions | Chat opens from the service snapshot. Text, replies, corrections, room bursts and comment reactions go to the backend. The host can mute chat, delete comments, pin a topic and pin a comment. The existing stage banner presents one pin at a time. |
| Unsupported prototype controls | Speaking simulation and chat-error simulation were removed from visible actions. Participant removal uses the kick contract. Separate moderator assignment, stage invitations and translation would require additional contracts. |

## Deployment

Vercel serves the built browser directory. The user-service rewrite precedes the broader voice rewrite. The SPA fallback targets Angular's emitted `index.csr.html`. Private API responses use `Cache-Control: private, no-store`. Static assets have independent cache rules. The local Express server supports streamed requests and responses. `USER_SERVICE_URL` and `VOICE_SERVICE_URL` override its upstream origins. Vercel uses the destinations in vercel.json. Node's system CA option allows the local proxy to trust the workstation trust store while validating TLS. [Vercel rewrites](https://vercel.com/docs/routing/rewrites)

Each Render blueprint builds its service Dockerfile, uses the cloud profile and exposes liveness. The frontend Auth0 audience and tenant match the blueprint values. Auth0 must allow the actual application origin as a callback, logout URL and web origin. The voice service needs LIVEKIT_URL, LIVEKIT_API_KEY and LIVEKIT_API_SECRET. Configure the webhook on the LiveKit project against the Render voice origin. Browser signaling and WebRTC media bypass Vercel. SSE runs over the HTTP rewrite and can reconnect if a proxy cuts the stream.

The cloud configuration contains database connection credentials in source. Before treating this deployment as production-ready, move the database and Redis credentials into Render secrets and rotate the existing values with the database operators. This requires coordinated infrastructure access and changes to both service configurations. No credentials are included here.

One backend reliability issue remains in comment moderation. CommentRepository pins and unpins by reading the Redis list, finding an index in the returned copy, then writing to that index with LSET. Concurrent deletion or trimming can move the index before the write. An atomic operation that checks the comment ID and updates its pin would preserve the existing API. This finding comes from source inspection.

The web audio processor uses the official Krisp package on a local microphone, checks browser support and reads the processor's enabled state. Echo cancellation, automatic gain control and browser noise suppression remain available independently. Enhanced processing depends on the browser, LiveKit deployment, model access and project entitlement. Billing and compatibility need checking against the selected plan. [LiveKit noise cancellation](https://docs.livekit.io/transport/media/noise-cancellation/) · [LiveKit Cloud comparison](https://docs.livekit.io/intro/cloud/)

## Verification scope

- Fresh Gradle test runs passed with 89 user-service and 159 voice-service tests. These use local test resources including PostgreSQL and Redis. They do not establish deployed media quality or webhook delivery.
- The Material frontend passed Angular production compilation, TypeScript checking, ESLint and 102 tests across 48 files. A room-session test exercises join, publish permission, microphone mute, promotion, reconnect snapshots, a threaded correction and leave using Angular HTTP testing and a substituted LiveKit connector. The production bundle exceeds the initial warning threshold of 1 MB (about 1.23 MB). The lazy Krisp chunk adds a separate first-use download.
- In a fresh headless Chrome session the built app redirected an unauthenticated room route to the landing page and the sign-in button navigated to the configured Auth0 tenant. The local preview served an existing legacy avatar and a Material preset. Both the built preview proxy and the Angular development server returned 401 problem responses from each backend using the workstation trust store.
- Both direct Render liveness endpoints returned 200. Both protected API probes returned 401 problem JSON. The configured legacy origin at jtalk-mocha.vercel.app returned HTML for the root and a deep route, and 401 problem responses for both proxied APIs. Both direct Render services accepted GET preflight with Authorization from that origin. Earlier cold probes timed out. These observations establish anonymous behavior only.
- No OpenAPI generator, checked-in specification or Swagger route was found in either service. Anonymous probes of /swagger, /swagger-ui and /openapi.json returned 401 from both services. A 401 alone cannot establish route existence. Use the controller-derived API reference.
- The local legacy checkout (06f530c) built, with five existing chat-panel lint errors and a spec referencing obsolete pinned/unpinned outputs. The remote legacy HEAD (ffae6aa) was checked independently in an isolated copy. Its lint, production build and 839 tests passed. Its combined check stops on formatting in CLAUDE.md and index.html. The backend revisions in the contract index matched their remote HEADs.
- Release acceptance remains open for authenticated registration and callback, two distinct participant sessions, actual device switching and audio, mobile autoplay, host moderation, real network loss, paid-model entitlement and cross-client state after reconnect. The probes above cover the existing deployment. They do not publish or validate this revision on Vercel.
